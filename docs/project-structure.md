# Project Structure

This document describes the purpose of the main directories and files in the Nekuvio repository.

## Top-Level Structure

```text
.
├── src/
├── scripts/
├── submodules/
├── patches/
├── test/
├── docs/
├── Dockerfile
├── compose.yaml
├── package.json
├── package-lock.json
└── tsconfig.json
```

## `src/`

The `src/` directory contains the application source code.

```text
src/
├── api/
├── generated/
├── pipeline/
└── ...
```

### `src/api/`

Contains integrations with external APIs and services used by Nekuvio.

### `src/pipeline/`

Contains application logic related to the media/data processing pipeline.

### `src/generated/`

Contains source files generated or maintained outside the main application source.

This includes build metadata generated by Nekuvio itself and generated Nekobt metadata provided by the badge submodule.

Generated files in this directory should not automatically be assumed to be hand-maintained source code.

## `scripts/`

Contains development and build-time scripts.

The main current script is:

```text
scripts/generate-build-info.ts
```

It generates GitHub-related build metadata before TypeScript compilation.

The script is intentionally executed during the build rather than by the running application.

## `submodules/`

Contains external repositories consumed by Nekuvio as Git submodules.

Currently:

```text
submodules/
└── nekuvio-badges/
```

The badge repository owns generated badge assets and related metadata independently from Nekuvio.

Nekuvio consumes a specific revision of that repository through the Git submodule.

## Badge Metadata Symlink

The generated Nekobt metadata is physically maintained by the badge submodule but exposed through Nekuvio's source tree:

```text
src/generated/nekobt-metadata.ts
    └── → submodules/nekuvio-badges/src/generated/nekobt-metadata.ts
```

This is intentional.

The TypeScript configuration uses:

```text
rootDir: ./src
```

A direct import of the source file from the submodule would place the imported source outside the configured source tree.

The symlink allows TypeScript to resolve the file through `src/generated/` while the actual generated file remains owned by the badge repository.

The submodule must therefore be initialized for a complete checkout of the project.

## `scripts/generate-build-info.ts`

This script generates:

```text
src/generated/build-info.ts
```

The generated file contains information about the GitHub revision associated with the build and the corresponding base URL for GitHub-hosted assets.

The application imports this information through `src/environment.ts`.

The complete design is documented in [GitHub-hosted assets and build metadata](architecture/github-assets.md).

## `patches/`

Contains patches applied to dependencies through `patch-package`.

The patches are installed as part of the normal dependency installation process.

## `test/`

Contains the automated test suite.

Tests are executed through:

```bash
npm test
```

## `docs/`

Contains project documentation that is not intended to be part of the normal user-facing README.

```text
docs/
├── architecture/
│   └── github-assets.md
├── development.md
├── project-structure.md
└── versioning.md
```

Architecture documentation records decisions and their reasoning.

Development documentation describes how to work with the project.

Project-structure documentation describes how the repository is organized.

Versioning documentation describes how application versions relate to Git tags, builds, and release artifacts.

## Root Configuration Files

### `package.json`

Defines the package identity, dependencies, supported Node.js/npm versions, and npm scripts.

It is also the source of application metadata such as:

* package name
* display name
* version
* addon ID
* repository URL

### `package-lock.json`

Locks the dependency tree used by `npm ci`.

It should be committed alongside `package.json`.

### `tsconfig.json`

Defines the TypeScript compiler configuration.

The project uses:

```text
rootDir: ./src
outDir: ./dist
module: NodeNext
moduleResolution: NodeNext
```

### `Dockerfile`

Defines the multi-stage Docker build used to produce the Nekuvio runtime image.

### `compose.yaml`

Provides the Docker Compose configuration used for local containerized development and can also be used by release automation with a different `IMAGE_TAG`.

## Source of Truth

Where possible, application metadata should have a single source of truth.

For example:

```text
package.json
    │
    ├── name
    ├── displayName
    ├── version
    └── addonId
```

Build-specific GitHub information is generated separately because it depends on the exact Git state of the build.

This distinction keeps static application identity separate from information that is specific to a particular build.
